The existing variable-count/width Pattern swatches are byte-identical drawing code. Below them the current Hue core evaluates neutral scene-linear DWG(Y,Y,Y), Y=.18*2^EV, EV-6..+6 in129points. One resultant curve has vertical generated-opponent-radius/Y, direction-key line colour, and actual output strip normalized to Y=.18 and converted to sRGB. No swatch-direction retention or output RGB tone-curve interpretation. Hue only: input/output profile selectors, Comp, Skin, Density and FinalSat do not change this fixed working-space reference.

Current pmvn_hue_curve is called directly; no approximate alternative Hue formula. Delta output-minus-neutral XYZ is converted through current Rec2020/opponent helpers. Line colour normalizes the zero-Y delta direction through XYZ->sRGB and sRGB transfer; it is a key, not output RGB. The strip is output XYZ normalized to Y=.18, then sRGB with0..1 display clip. CLIP footer signals any out-of-display-gamut samples. Plot range auto-expands to1/2/5/10/etc and prints max; no amplitude clipping. Different auto-ranges must be read numerically, not compared solely by line height. No tone/gamut mapping. This cannot predict arbitrary coloured-image output, all Pattern sector behaviour or perceptual saturation.
